# CLAUDE.md

Guide for Claude Code (and humans) working in this repository.

## What this is

`loci` is the engine for an agent harness that helps scientists run geospatial workflows they can
trust. Phase 1 is a Python package exposed as an MCP server and used from Claude Code, with
verification and provenance built in from the start. A map-first IDE comes later and will be built
on the same tool interfaces.

Guiding question for every feature: **does it help a scientist ask a better question, trust an
answer, or make a decision?**

## Commands

```sh
uv sync                    # create .venv and install the package plus the dev group
uv run pytest              # tests (network tests deselected)
uv run pytest -m network   # only tests that need internet access (Sentinel-2 over Sydney)
uv run ruff check          # lint
uv run ruff format         # format (CI runs `ruff format --check`)
uv run mypy                # type-check src/ and tests/
```

Run lint, format, mypy and pytest before every commit. CI runs the same checks on Python 3.12
and 3.13.

## Layout

```
src/loci/        the package
  io/            readers: files, URLs and STAC items -> xarray Dataset or GeoDataFrame  [M1, M3]
  summary/       compact summaries of loaded data                                        [M1]
  checks/        geospatial invariants and the runner behind `validate`                  [M2]
  tools/         tool functions: Workspace + plain args -> pydantic result models        [M1+]
  models.py      result models: the stable interface for MCP and a future UI             [M1]
  workspace.py   data_ref registry on disk under .loci/                                  [M1]
  synthetic.py   fixture writers with exactly known answers (tests and benchmarks)       [M1]
  render.py      PNG drawing behind `preview`                                            [M3]
  provenance.py  provenance records: ledger under .loci/provenance/ plus file sidecars   [M4]
  script.py      helpers for scripts started by `run` (read, physical, save)             [M4]
  server.py      thin MCP wrapper over tools/                                            [M5]
tests/           pytest suite; fixtures are generated in code by loci.synthetic
benchmarks/      five benchmark workflows and run.py                                     [M6]
docs/DECISIONS.md  decision log
```

## Rules

- **Large data never enters the model context.** Tools load and hold data in the workspace and
  return a compact summary plus a `data_ref`. Later tools take `data_ref` values as inputs.
- **Tool signatures and `models.py` are a stable interface.** Change them deliberately and record
  why in `docs/DECISIONS.md`.
- **Layering.** Core code (`io/`, `summary/`, `checks/`) works on xarray and geopandas objects and
  knows nothing about refs or MCP. `tools/` adds workspace handling. `server.py` only adapts
  `tools/` to MCP.
- **No silent guesses.** Assumptions (for example an assumed CRS) are flagged in results. Nothing is
  reprojected, resampled or dropped implicitly.
- **General across data types.** Rasters, vectors and point data are all first-class, not only
  Earth observation.
- Small, typed functions. Tests go alongside code, using synthetic fixtures with exactly known
  answers from `loci.synthetic`. Fixtures are generated by code, not committed as binaries.
- Warnings are errors in tests. Filter a third-party warning only by its exact message, and only
  when it is harmless.
- Import each tool from its own module (`from loci.tools.load import load`). `loci.tools` does
  not re-export them, because that would shadow the modules of the same name.
- New checks are small functions in `checks/` that take `Layer`s and return a `CheckResult` with a
  stable id. Test each one on a fixture built to pass and one built to fail. `checks/runner.py`
  decides where it applies.
- STAC loads never resample or reproject on their own: mixed resolutions or CRSs are errors until
  `resolution=` or `output_crs=` is given, and whatever was done is recorded as a note.
- Every new data_ref or file a tool makes gets a provenance record (`loci.provenance`) naming its
  inputs, so `lineage` can trace it. Scripts for `run` read data only through declared inputs;
  `script.read()` gives physical values, and `raw=True` is for bands that must stay as stored.
- Add tools only when a benchmark task needs them. Ask before adding substantial dependencies.
- Record significant decisions in `docs/DECISIONS.md`: one short entry with context, choice and
  alternatives.
- Prefer clear and boring over clever. Make small, descriptive commits.

## Working style

Work one milestone at a time. At the end of each, summarise what was built and tested and list open
questions, then stop. When something is ambiguous, ask rather than guess.
